# Pragma punctuation

- **Filtered transclusion closures:** A widget tag whose attribute ends in a filtered transclusion (`{{{ ... }}}`) takes a single closing `>` — `<$let name={{{ [filter] }}}>`. A double `>>` leaks a stray `>` text node into the output; a bare `}}}` leaves the tag unterminated and swallows following content.
- **Macrocall with a `<var>` last parameter:** `<<proc p:<var>>>>` — the variable's closing `>` runs into the macrocall's `>>`, and the terminator lands early, leaking a stray `>` text node(project-view References section). Put whitespace before the closer: `<<proc p:<var> >>`. (Attribute position is immune: `attr=<<var>>` followed by the tag's `>` parses correctly.)
- **Existence gates:** `is[tiddler]` matches non-shadow tiddlers ONLY (`wiki.tiddlerExists()` excludes shadows — verified empirically; the docs' `is.tid` table is correct) — never use it to gate on plugin-shipped members. `has[title]` matches real OR shadow tiddlers and is the docs' recommended either-form: `[[title]has[title]]`. (`get[title]` also resolves shadows but reads indirectly.)
- **Macrocall parameters do not evaluate `<var>` indirection:** `<<proc p:<varname>>>` passes the LITERAL string `<varname>`(modal prefilled "Of project" with `<currentTiddler>`). To pass computed/variable values to a procedure, invoke it as `<$transclude $variable="proc-name" param=<<var>> />` — widget attributes DO evaluate `<<var>>` (the pattern `$hgsd.list` uses for `hgsd-render-inner`).
- **Multi-attribute `$let`/`$set`:** Non-final attributes end `}}}` with no `>`; only the final attribute carries the tag-closing `>` (`...}}}` newline `...}}}>`).
- **Plain HTML tags need their `>`:** An unclosed tag (`<optgroup label={{...}}` followed by a newline) absorbs the NEXT tag's attributes into itself — the following `<option>` vanishes and its `value` lands on the wrapper (References.tid once shipped three such optgroups, silently offering only half the sort options). Assert wrapper CHILD ELEMENT counts in render probes, not descendant option counts.
- **`:and` with an input-ignoring operand:** `filterrunprefix and.js` `pushTop`s the operand output; an operand starting with a `<var>` run ignores its input iterator, so `[possibly-empty] :and[<flag>match[x]]` yields `["x"]` even from an empty pipeline. Use `:filter[<flag>match[x]]` (input-driven) for compound `<%if%>` guards.
- **Pragma parameter defaults:** A `)` inside a parameter default (e.g. `none-group-label:"(none)"`) terminates the pragma parameter list — the widget body is silently truncated from that point. Use a blank default plus a runtime fallback in the body instead.
- **Variables carrying lists:** `$let` via `{{{ }}}` assigns a multi-valued variable; `<var>` in a filter reads only its FIRST value — and so does `enlist<var>`(a multi-valued `mv` yields just `alpha` under `[enlist<mv>]`). Titlelist strings remain the reliable full-list transport for VARIABLES, but 5.4 adds two more (docs: variables/Multi-Valued Variables): `[(var)]` retrieves all values as a filter run, `((var))` passes them through attributes/parameter defaults — and in practice a `\function` returning a list, called as `[function[fn],[param]]` (comma-separated positional params), carries sets end-to-end without either (the HyperGSD status tag list). `:map[subfilter]` keeps only the FIRST output per input item — use `:and[get[field]split[ ]]` chains for 1:many mappings.
- **A filter error literal is TRUTHY output:** a broken filter renders/returns the string "Filter error: …" as its result, which passes `!match[]` gates and flows into operators as an operand (a type name became "Filter error: Missing [ in filter expression" and gates opened/closed on it silently). Guard renders with a `/Filter error/.test(text)` assertion; treat its presence as a hard failure. Chief cause here: multi-run filters need NO outer bracket — a stray trailing `]` after a complete run (`:and[get[x]]]`) silently breaks the whole filter while every sub-probe "works". Bracket-count every hand-written `] }}}` ending. The quoted-attribute sibling: a filter attribute ending in a bracketed run closes it ONCE before the quote — `…]">`, never `…]]">`; the doubled form is easy to write because a union run's own `]]` looks like the pattern. Detection tell: inside a `<$list>`, a parse-broken filter does not throw — the error STRING becomes the single iterated item, so a garbage tiddler titled `$:/temp/alert/Filter error: …` gets created; assert `/Filter error/` absent from any raised list output.
- **Operator chains after a closed literal run are silently dropped**: `[[base]]addsuffix<x>addsuffix[[-]]addsuffix<y>` parses the first run, then treats each `addsuffix…` bare word as ANOTHER TITLE — no error, and a filtered-transclusion attribute takes the first item, so the value is just `base` and the chain never runs (listState titles and Cleanup's timeout carried this bug; uniqueness held only via the qualify hash). The whole chain must sit INSIDE one outer bracket pair — `[[base]addsuffix<x>addsuffix[-]addsuffix<y>]` — with plain single-bracket literal operands (`addsuffix[-]`, not `addsuffix[[-]]`, whose inner `]]` closes the run early). Probe any chained title-assembly filter by evaluating the full string, not its pieces.
- **`op[]]` inside a quoted widget attribute breaks the attribute scanner**: a filter text embedded in a quoted attribute value and ending a run with an empty operand (`match[]]`, `unique[]]`) leaks `">"` as literal text into the render — even though the same string works inside a `$let`-quoted attribute. Avoid empty-operand runs at attribute-text ends: use a negated run (`-[tags[]prefix[x]]`) or a trailing no-op run instead. A sibling parse trap, hit in the same work: `get[text]enlist-input[]` followed by a space and a NEW run (`…enlist-input[] -[<var>]`) is a parse error ("Filter error: Missing [ in filter expression") — keep the whole chain inside one run, or let `$action-listops` over the field parse the list for you. Related recurring trap: a multi-attribute `$let` whose final `{{{ }}}` attribute carries TWO closing chevrons (`}}}}>>`) emits one stray `>` per render — grep `}}}>>` (expect zero) after every wikitext edit touching filtered-transclusion attributes, and give macrocall attributes before a tag close a protective space (`attr=<<var>> >`).
- **Procedures as `subfilter<>` operands:** a parameterless `\procedure` with a text body works exactly like a `\define` in `subfilter<name>` (realm-scopes/type-gate are converted examples). Prefer procedures/functions over `\define`.
- **`subfilter` passes its incoming SOURCE through** (filters/subfilter.js: `filterTiddlers(operand, widget, source)`): the inner filter's first run receives whatever the outer context accumulated, not the default all-tiddlers source. A filter evaluated mid-pipeline (inside `:filter[...subfilter{!!field}]` gates, where the source is one tag-list member) must therefore START with a selection operator (`all[tiddlers]`) — starting with `tag[]` silently filters the member and always returns nothing (HyperGSD warning conditions). The same source pass-through is why a filter evaluated at the TOP of a widget (`[subfilter<list-filter>...]` as the first operator) DOES get the default source — and with it the tag index: `wiki.each` (the default source) carries `byTag`, which `tag.js` returns directly, while an explicit `[all[tiddlers]]` prefix produces a plain array whose iterator lacks `byTag`, forcing a full-wiki `indexOf` scan + `sortByList` per evaluation. Rule: leading `tag[]` at top level (index path), leading `all[tiddlers]` inside subfilter-from-a-source contexts (source reset).
- **`enlist[a,b]` is ONE item, the literal string "a,b"**: `parseStringArray` splits operands on SPACES; commas belong to filter operand SYNTAX (`op[a],[b]` = multiple operands, and enlist reads only the first). Space-separated `enlist[a b]`, comma-less runs (`[[a]] [[b]]`), or comma-params on `function[]` calls are the working forms. Related: a `:filter[...]` run evaluates per input WITHOUT rebinding `currentTiddler` — `all[current]` inside it still means the ambient tiddler; reference the input through input-driven operators (`tag[]`, `tags[]`, `get[]`) instead.
- **Functions:** invocable via `<<fn param>>` in text AND `{{{ [<fn param>] }}}` in filter transclusions. A stylesheet-only helper belongs as a FILE-LOCAL `\function` pragma in the stylesheet tiddler — narrower than any Global tag (stylesheets render at page level, seeing only root imports).
- **Bare-rootWidget fakeDOM renders overstate widget-heavy stylesheet costs ~50×:** a `$list`/`$let` body inside a stylesheet rendered with `parentWidget: $tw.rootWidget` alone hit a pathological resolution path (1ms → 245ms); the SAME parse through the importvariables G-chain takes ~4ms, matching production's page-level imports. Always G-wrap stylesheet benchmarks/renders.
- **`<$transclude $variable>` passes parameters even to legacy `__param__` defines** — verified against kookma's move-to-trashbin (the `\import` + macrocall form and the transclude form are interchangeable).
- **Negated `-enlist[...]` runs do not parse** ("Filter error: Missing [ in filter expression"): exclude titles with negated runs instead (`-title -text -tags`), each its own run.
- **The `+` run prefix REPLACES the accumulator — it does not append** (filterrunprefixes/and.js clears the results before pushing the run's output; the run executes over the accumulated titles). With a source-filtering operator (`!prefix[]`, `tag[]`) that is an intersection; with an input-ignoring operator (`list[]`, `enlist[]`) it is wholesale replacement. Union/append is a NO-PREFIX run. Worked failure: `$action-listops $tags='+[!prefix<p>] +[list<ref>] +[unique[]]'` composes as `<oldtags> +[…]…` — the `+[list<ref>]` run overwrote the kept tag with the pick alone, untagging the member from its tag list so the row vanished from both the Settings draggable and the panel. Fix: leave the list run unprefixed (`… +[!prefix<p>] [list<ref>] +[unique[]]`).
- **A seed title placed BEFORE a `:and` chain is dead weight — position decides survival** (`:and` replaces the accumulator, wiping everything before it; only plain runs placed AFTER the last replacing run union into the final result). Worked failure: `[<tag-list>addsuffix[/Portion/1]] [<tag-list>] :and[tagging[]] :and[tags[]prefix…] +[unique[]…add[1]]` — the seed run sat before the `:and` pair, so it was ALWAYS discarded; the expression still passed every test where the `:and` enumeration was non-empty (the tags alone carried it) and only went empty when the enumeration was — the exact case the seed existed for — leaving `next-free-portion-tag` a malformed `…/Portion/` title that rendered as a blank-labelled option. Fix: move the seed AFTER the replacing runs (`… :and[tags[]prefix…] [<tag-list>addsuffix[/Portion/1]] +[…]`). Symptom signature: an expression with a fallback/seed that works on populated data and silently yields blank on empty data — the empty-enumeration case is the one that must be tested, and gap-shaped fixtures pass by coincidence.
- **SelectWidget has no `value` attribute** — the current-selection attribute is `default=` (a `value=` is silently ignored, so the control renders with nothing selected). Its change handler writes the bound tiddler/field BEFORE invoking `actions`, and passes NO value variable — the chosen value must travel through the tiddler the select writes (read it back with `list[<state!!text>]` in a variable operand). `$select` passes `class` through to the element but no `id` or other foreign attributes — a `<label>` association must WRAP the control, `for=` cannot reach it.
- **An operator after a run's closing bracket ORPHANS at run level** — `… :and[tag[X>]limit[1]]` closes the `:and` run at the first `]`, then `limit[1]` parses as the bare TITLE `limit` plus a title run `1`, both union-ed into the result, so the gate is ALWAYS truthy (silent: it rendered empty-but-present band divs on unclaimed tag lists until a test finally asserted absence). Chain the operator INSIDE the run: `:and[tag<X>limit[1]]`. Symptom signature of this class: a `<%if%>` gate that never goes false while the equivalent inner `<$list>` loop correctly renders nothing.
- **Inside a procedure invoked from a widget's `actions` string, a macro-style `<<param>>` attribute makes the action widget NEVER INVOKE** — silently (no error, no write; SetFieldWidget's `actionTiddler` stays empty and `invokeAction` skips). Filter expressions resolve reliably there: filter attributes (`$tiddler={{{ [<param>] }}}`), `<%if%>` conditions, and `$let`-locals created inside the procedure all evaluate; body-level `$let` variables also resolve (the picker popup-close's `<<pop>>`); a bare `<<proc>>` as the first thing in an actions string fails too (invokeActionString parses BLOCK mode and macrocallblock requires an end-of-line after the call — invoke a procedure with `<$transclude $variable="…"/>`). Worked failure: the identical `<<param>>` attribute fired in a plain-body actions string but died through the procedure hop; every dynamic attribute became a `{{{ }}}` filtered transclusion to fix it.
- **`get[text]!match[x]` is FALSE when the tiddler is MISSING** — the negated match filters the run's input titles, and `get[]` over a missing tiddler emits nothing, so no titles survive to mean "not x". Materialise a value with an else operand — `get[text]else[no]!match[yes]` — the shipped preserve-action gate's idiom, needed for the pointer gate over the often-absent `$:/info/browser/pointer-coarse`.
- **A `:filter` subfilter must start BARE — a leading bracketed run is a parse error** ("Missing [ in filter expression", silently fatal inside widget attributes): `:filter[[<currentTiddler>…]]` breaks; `:filter[<currentTiddler>addprefix[$:/config/x/hidden/]get[text]else[show]match[show]]` works — candidate as a variable SOURCE run, everything else literal operands chained after it. Inside the subfilter, `currentTiddler` IS the candidate.
- **Table rows cannot span a widget boundary:** wikitext tables parse from consecutive `|` lines in ONE block context — a `<$list>` (or any widget) between the header row and the body rows splits them into SEPARATE tables (the header renders alone; each iteration's row parses as a paragraph beginning with a literal `|`, so no `<tr>` is ever produced). Generating table rows per item means writing the rows LITERALLY (one per item, compositions inlined per row), not looping. Widgets INSIDE a cell are fine (`|<$let …><span …>…</span></$let> |…|`); it is row-level wrappers that break the table.
- **`first[1]` over multi-run candidate lists is order-fragile, and empty variables win silently**: a run reading an empty variable emits the EMPTY STRING as a title, which `first[1]` happily returns (and `format:titlelist[]` DROPS it, so accumulator dumps lie); duplicate titles across plain runs reorder under pushTop dedup. The robust fallback-chain idiom: one run per stage, each emitting its own candidate via `then<candidate-variable>` behind a config lookup (`[<candidate>addprefix[base]get[text]else[show]match[show]then<candidate>]`), and ship the lookup BASE tiddler itself reading `hide` so an empty candidate is withdrawn by construction.
- **Core's `$checkbox` renders label-rooted DOM** (`<label>` wrapping `<input type="checkbox">`): fakeDOM walkers must match `domNodes[0].tag === "label"` containing the input — matching the input as the widget's root finds nothing.
- **Pointer (or any media) detection needs no JavaScript**: a tiddler tagged `$:/tags/MediaQueryTracker` with `media-query` + `info-tiddler` fields makes core's mediaquerytracker.js write yes/no to the info tiddler at boot and on every matchMedia change (core's own `$:/info/browser/darkmode` mechanism). Browser-guarded (`if($tw.browser)`), so Node harnesses leave the info tiddler absent — which doubles as the non-matching branch in tests.
- **Config-shadow `.tid` bodies must end WITHOUT a trailing newline** — `match[true]` compares exactly and `"true\n"` fails silently. shadow-newline-test guards every ui/config body (it caught a freshly written tracker tiddler).
- **Never boot a live user wiki in a bare node process:** third-party plugins register background actions + filesystem syncers that DISPATCH SAVES on startup (observed: a $:/StoryList write). Analyse user data via the running server (playwright) or by parsing tiddlers/*.tid files directly.
- **Wrappers pull their dependencies into their own context:** a Global/View-scope rule can be broken by a MODAL-side wrapper that transcludes the shared component (status-radios.tid must stay Global because the modal wrapper renders it inside a modal). When auditing scopes, grep consumers excluding the definition file by EXACT path — a substring filter once hid the wrapper (`grep -v components/status-radios` excluded both files).
- **Never patch a macrocall attribute adjacent to a tag-closing `>` by string replacement without recounting the chevrons** — replacing `<<x)>>` with `<<x>>` silently consumed the following `>` in one edit, leaving the tag unterminated; everything after was absorbed as attributes and the tag's class remnant + `</svg>` leaked as literal text. Prevention: order macrocall attributes FIRST and quoted literals last, closing the tag after a quote (the plugin images' pattern).
- **Literal tag text in extraction output is NEVER an artefact** — `"></svg> 2 days from now` in a fakeDOM text dump was a real broken-icon render, not extraction noise. Assert icon presence as ELEMENT nodes (`tag === "svg"` counts) plus a zero-literal-svg-text guard; a bare `/from now/` regex on textContent passes while the icon is broken.
- **A `display` declaration on a reveal wrapper class overrides the `[hidden]` attribute hiding** (same specificity, plugin stylesheet loads after core): a CLOSED `$reveal type="popup"` renders an empty wrapper with `hidden="true"` — give the wrapper class a guard rule (`.my-popup[hidden] { display: none; }`) or the empty box shows permanently ("the glowing box"). Core's reveal is also LAZY: `execute()` builds children only when open at render; closed→open content appears via `updateState` on refresh — so probe reveals in BOTH the rest and click-through states.
- **A let-bound fallback value goes stale by one interaction**: a pick→clear sequence reverts to the pre-pick value because the fallback read the field at render time. Read the field at ACTION time inside the value filter instead (`~[<target-tiddler>get<target-field>]` — the TiddlyTools save's own pattern).
- **`$hgsd.list`'s `<$refresh>` whitelist gates state tiddlers away from row subtrees** — any state-driven reveal inside a list row (popups!) never learns its state changed unless the fragment declares its prefixes in an `hgsd-refresh-whitelist` field; the gates compose those fields into every layer above the rows too (the tickler popup prefix is the worked example — one field on the fragment, no main-plugin entry).
- **Definition scope tags:** `$:/tags/Global` = everywhere (root import); `$:/tags/Global/View` = ViewTemplate subtree + preview only (imported by core's ViewTemplate.tid) — anything reachable from a MODAL must stay Global (modals mount at page level outside view imports). Pick the narrowest tag whose consumers all render inside it. Harnesses must import each tag explicitly in their G chain — the bare headless root widget carries nothing ("Undefined widget 'hgsd.list'" without it).
- **Stylesheet rendering:** core wikifies stylesheet tiddlers into a `<style>` element and consumes its TEXT — transient inline markup (hex values linkify as missing-tiddler spans in HTML renders) vanishes in textContent. Assert stylesheet output on the style element's text, never on `renderTiddler("text/html")`.
- **A `display: none` print rule at (0,1,0) loses to any equal-specificity display rule in a stylesheet sorting later** in the `$:/tags/Stylesheet` tag list (alphabetical by title; `list-before`/`list-after` pins work, but sub-plugin titles are not yours to order): print rules must target elements with NO display declaration of their own — put the print hook on a display-rule-free wrapper (pick-append's add-row wrapper) rather than escalating specificity; a compound selector works but silently depends on tag-list order.
- **The wikitext table parser emits `align` attributes from cell padding** (`| A |` → `align="center"`, one-sided padding → left/right — table.js), and a presentation attribute loses to ANY author CSS: core's `.tc-control-panel table > tbody > tr > td { text-align: start }` un-centres padded cells inside the control panel while the story river keeps them centred — a class rule on the table restores it in every context.
- **`<$text>` inside a quoted attribute value is literal text, not a widget** — the parser never evaluates widgets inside attribute strings (only `{{{ … }}}` filtered transclusions and `<<macro>>` calls). CSS like `option[value="<$text …/>"]` ships the literal markup; write `option[value="{{{ [<variable>] }}}"]`.

# Procedures and widgets

- **`<%if%>` conditionals in preference to `<$list>` guards** when a filter is used only for its truthiness — `<$list>` rebinds `currentTiddler` to its loop variable, which shadows ambient scope inside the body.

# Performance

- **Widget-level caching**: Within widgets, use `<$let>` or `:filter` runs to avoid re-scanning the entire wiki multiple times.
- **Asset caching**: Cache prefix/suffix lookups outside of loops in dashboard lists.
- **Literal filters for cacheability**: Keep filters passed to frequently rendered widgets free of dynamic variables where possible, so TiddlyWiki can cache the parse tree.

- **Benchmarks need targeted reruns:** a first full-suite before/after pair showed an ~11% heavy-dashboard construct "win" that did not reproduce under repeat runs of that bench alone — warm-up noise. Confirm any reported delta with repeated runs of the specific bench, not single suite passes.

# Shadow tiddlers

- Tiddlers in `tiddlers/` override tiddlers with the same `title:` field from plugins. A shadow for `$:/plugins/Foo/ui/bar` would be in a file named `$__plugins_Foo_ui_bar.tid`, but it's the **title** inside the file that controls the override — the filename convention is just for discoverability. To find one:
  ```bash
  grep -rl 'title: $:/plugins/Foo/ui/bar' <wiki-folder>/tiddlers/
  ```
  **Do not blindly delete shadow tiddlers without asking first** — they may contain intentional overrides.

# Filter expression pitfalls

## Filter chains are AND, not OR
Consecutive filter runs are chained with AND logic — each run filters the output of the previous. `[A] [B]` means "keep only results that match BOTH A and B", not "results from A OR B". Use `else` for OR-like branching.

## `else` chains with subfilters
`else` takes the rest of the filter run (until the next `else` or closing `]`) as its subfilter. The subfilter starts from an empty pipeline:
```
[get[field]else<variable>match[value]then[output]else[different-output]]
```
A bare `<variable>` inside an `else` subfilter correctly adds the variable value to the pipeline. Do **not** wrap it in extra brackets — `else[<variable>]` treats the variable name as a literal string.

## Indirect attribute + self-closed child leaks the closer as text
`<$tiddler tiddler=<<var>>><$transclude field="caption"/></$tiddler>` parses
BROKEN: the `>>>` (indirect value's `>>` + tag close) followed by a
self-closed child widget makes the `</$tiddler>` closer a literal text node —
functional-looking output with a stray-markup leak. The body'd form is safe:
`<$tiddler tiddler=<<var>>><$transclude field="caption">fallback</$transclude></$tiddler>`.
Found via the stray-markup audit; exact cause inside the widget
attribute scanner unconfirmed.

## `<%if%>` does not fire inside `actions=""`
Neither `<%if%>` nor `<$list>` conditionals execute inside the `actions` attribute of `<$select>`. The `actions` string can contain `$action-setfield` with filter-based values (via `{{{ }}}`), but control-flow widgets are silently ignored. Put complex defaulting logic in the submit procedure instead.

## Action attributes evaluate at invoke; a `$let` wrapping them evaluates at render
`Widget.invokeActions` refreshes (`refreshSelf`) only the ACTION children it walks — a `$let` between a button and its actions is propagated through (actions nested inside it do fire), but the `$let`'s OWN attributes evaluated when the panel rendered and are NOT re-evaluated at invoke. Two consequences: a `$let` before actions adds its filter evaluations to every panel render (the portion bench caught this as a measurable chassis cost — fork the buttons and use direct action attributes, whose filtered transclusions wait for invoke), and its values can be stale if the underlying state changed without a re-render. A `$let` INSIDE an `actions=""` string is the good half: the string renders at invoke, so the lets evaluate then — fresh, and free at render time.

## Empty strings are not "empty" in filter pipelines
If a field exists but is set to `""`, `get[field]` returns `[""]` (one item: the empty string). This is NOT an empty pipeline, so `else` will not fire. To check whether a field actually exists (vs being empty), use `<%if%>` with `has[field]`:
```
<%if [<tiddler>has[gsd_status]] %>
  <!-- field exists (even if empty) -->
<%else%>
  <!-- field does not exist -->
<%endif%>
```

## `get` on a missing field yields no output
`get[field]` on a tiddler lacking the field produces an empty pipeline (unlike `field[field]` which yields ""). Combine with care: `[all[current]get<field>]match[]` matches BOTH missing and empty; `!match[]` matches neither.

## Negated `field:` drops tiddlers whose field is absent
`!field:X[Y]` matches only tiddlers where field X EXISTS and differs from Y (verified in core/modules/filters/field.js: the branch requires `text !== null`). So "field absent counts as not-Y" must be spelled `:filter[get[X]else[default]!match[Y]]` — e.g. open-item checks treat a missing `gsd_complete` as open via `get[gsd_complete]else[false]!match[true]`.

## `else` before a positive `match` is redundant; before a negated one it is load-bearing
`get[f]else[false]match[true]` ≡ `gsd_complete[true]`: a missing field yields no output in both forms, so the positive test fails either way — drop the `else` (or use the plain field selector). But `get[f]else[false]!match[true]` and `get[f]else[false]match[false]` REQUIRE the else: without it a missing field leaves no title to test, so the item drops instead of counting as "not f". Test positives bare; materialise defaults only for negations and `match[false]` positives.

## The default filter source is title-sorted — a trailing `sort[title]` over it is dead weight
`wiki.each` iterates `getTiddlerTitles()` — `Object.keys(tiddlers).sort(localeCompare)` (boot/boot.js) — and the tag index is built from that walk, so a leading `tag[X]` over a tag tiddler with no `list` field is already alphabetical and every selector after preserves the order. An appended `sort[title]` re-derives the order the engine already produced — verified identical rendered order through `$hgsd.list` with and without it, including a `sort[title]` "tiebreak" pre-sort before `!nsort[date]` (ties arrive alphabetical by construction, so the stable sort breaks them the same way either way). Removing the explicit sort also lets a user-pinned `list` field on the tag tiddler take effect (`sortByList` applies it inside `tag[]`). Sorts that remain real work: any non-title key (dates, statuses), pipelines over `all[tags]` (tag-map insertion order, NOT sorted), `:map` outputs (first-encounter order), titlelist fields (pick order) and union-of-runs orders.

## `!match[]` spacing
The negated match operator `!match[]` as a bare filter step requires a space after the preceding step: `get[field] !match[]` is correct; `get[field]!match[]` (no space) can cause parser errors.

## `match[...]then[value]else[value]` pattern
When starting a filter from a literal pipeline value, this pattern works correctly:
```
[[action]match<newType>then[next]else[active]]
```
For `newType = "action"`: `[action]` → "action" → `match<newType>` matches → `then[next]` → "next". For `newType = "project"`: `match<newType>` fails → `else[active]` → "active".

## Adding tags to a tiddler: prefer `tm-add-tag` with `$fieldmangler`

When you need to add tags to a tiddler (especially after creation), use `tm-add-tag` inside a `<$fieldmangler>`. This is the canonical TW approach and handles multi-word tags and special characters natively.

```html
<$fieldmangler tiddler=<<target-tiddler>>>
  <$action-sendmessage $message="tm-add-tag" $param=<<tag-value>> />
</$fieldmangler>
```

Avoid constructing tag strings with `join[ ]` in filter pipelines — TW's tag storage splits on spaces, so multi-word tags break unless wrapped in `[[...]]`, and the `format:titlelist` + `join` chain is fragile across TW versions. `tm-add-tag` sidesteps all of this.

## Variable scope: procedures vs filter strings in action widgets

Procedure parameters are template variables within `<%if%>` blocks and `<$let>` expressions in the procedure body, but they do NOT reliably resolve inside filter STRINGS passed to action widgets (`$subfilter`, `$tags`, `$filter`). Action widgets evaluate filter strings at action-time where the procedure's parameter scope may be unavailable — they can fall back to `currentTiddler`.

- **Safe**: `<%if [<param>!match[none]] %>` inside the procedure.
- **Unsafe**: `$subfilter="[<param>]"` on an action widget — `<param>` may resolve to `currentTiddler`.

To pass values into action-widget filter strings safely, bind them in a `<$let>` first and reference the let variable.

## `match[...]` is exact string equality
`match[]` compares the whole string, character for character. A shadow tiddler's body carries the `.tid` file's trailing newline, so `[[$:/config/X]get[text]]` yields `true\n` — which does NOT `match[true]`. Append `trim[]` after `get[text]…else[…]` before comparing text values. Values written by checkboxes/radios/buttons are clean and need no trim.

## `tagging[]` is input-driven and ignores its operand
`tagging[SomeTag]` does not select members of `SomeTag` — the operator maps each INPUT title to its tagging set and never reads the operand. Use the literal-input form `[[$:/tags/X]] :and[tagging[]]`, which also respects the tag tiddler's `list`-field ordering. Over multiple inputs (`[enlist<tags>tagging[]]`) it unions the tagging sets (pushTop dedupes). Dually, `tag[X]` tests whether each INPUT title carries X — it cannot drop a tag from a tag list; removing tags by title needs negated TITLE runs (`-[[X]]`, `-[<var>]` — the prereq-row shape), and chained `!tag[X]` filters by membership, not equality. Two adjacent discoveries: `[[$:/tags/hypergsd/Type]] :and[tagging[]] :and[get[hgsd-type]]` emits the type WORDS, not the member titles (the trailing `:and[get[]]` maps them — `getTiddler("action")` is undefined); and tag-index discovery (`all[shadows+tiddlers]tags[]prefix[x]`) only sees tags tiddlers actually CARRY, so an empty family vanishes — enumerate the tag TIDDLERS by title (`all[shadows+tiddlers]prefix[x]`) when a settings surface must list families whose members have not shipped (the Fragments tab's draggables and placement select work this way).

## Filter parser position rules
- `[[title]op[...]]` (literal with trailing operators) parses reliably only as a filter's FIRST run; mid-filter, a following `[[` restarts a literal scan that swallows to the next `]]`. Use `[title[X]…]` in any position.
- Prefix-run subfilters (`:filter[…]`, `:and[…]`, `:then[…]`, `:or[…]`) must start with a bare operator run — a leading space or `[` is a parse error ("Missing [ in filter expression").
- `then[<variable>]` / `else[<variable>]` do not parse (literal operands only). The ANGLE form does: `compare:string:lt<localToday>then<overdue-label>else<due-label>]` passes variable OPERANDS through `<>` and works (tickler banner titles — labels pre-bound in a `$let`, the condition on the item's date). For a value fallback keyed on input emptiness, use the `:then[enlist<variable>]` prefix run. Do not be fooled by shipped code carrying the broken form — it silently evaluates to a filter error. A bracketed FILTER inside an operand fails from the inside: `then[<pick-tiddler-title>get[hgsd-pick]]` ends the operand at the FIRST `]`, and the leftover becomes a parse error whose literal string — `"Filter error: Missing [ in filter expression"` — becomes the attribute's VALUE (an action-listops received it as its target tiddler and silently no-opped; the fakeDOM harness catches what the UI swallows). Derive through a `$let` with flat variable operands first, or fork.
- **A `$list` filter attribute cannot read `<currentTiddler>`**: `$list` owns `currentTiddler` as its iteration variable, so inside its own `filter=` the name resolves to the unborn loop variable — empty. `match<currentTiddler>` in a list filter matches nothing and rows silently vanish. Snapshot it in a `$let` above the loop (dependants.tid's `viewing-title` is load-bearing, not redundant); `all[current]` works only because it reads the variable at evaluation time elsewhere — do not assume the same for operand references inside the filter text.
- **`enlist<var>` splits its value on spaces**: a single title containing spaces ("New Person") enlists as two titles. To test a whole single-title variable, use a variable run (`[<typed-pick>!match[]] :and[!is[tiddler]]`), never `[enlist<var>!is[tiddler]]` — the enlist form wrongly passes existing multi-word titles.
- `$action-createtiddler` publishes `createTiddler-title` only to its own subtree at invoke time (`setVariable` + `refreshChildren`); sibling actions read it empty. Nest every follow-up action inside it (the modal's `create-gsd-tiddler` nests for this reason). In fakeDOM, fire a button with `widget.invokeActions(widget, {type:"click"})` — the canonical `handleClick` chain; walking children and calling `invokeAction` individually misses the propagation semantics.
- When grepping for the `}}}>` stray-`>` bug, the malformed shape is THREE braces + TWO angles (`}}}`+`>>`). A grep for four braces finds nothing and gives false confidence — verify endings with `grep -o '}}}[>]*'` and expect only `}}}` (tag continues) or `}}}>` (tag closes). Also: `[[Title ]` with a single closing bracket makes the literal scan swallow the rest of the filter (shows as "Missing [ in filter expression" leaking into rendered output) — bracketed literals need `[[Title ]]`.
- `:and[...]` does not short-circuit on empty input — it always evaluates its subfilter.
- **`:and` REPLACES accumulated output; suffix runs APPEND** — placing an `:and` chain mid-filter (e.g. a `[tags[]] :and[prefix[...]]` membership run after earlier runs in a `$refresh` whitelist) silently wipes everything before it and closes the gate. One `:and` chain per filter, and mind its position(the outer derivation gate initially placed a realm-membership run after the type-gate run and relevant changes stopped updating).
- **`$let`/`$set` filter-valued attributes recompute on EVERY refresh descent** into them (LetWidget.refresh → computeAttributes) — the cost is paid even when the value is unchanged, so an expensive derivation left outside a `$refresh` gate burns on every global edit (measured ~0.3ms × items × visible lists per cycle). Wrap the derivation itself in a gate whitelisting what it reads; deletions need an explicit `[!is[tiddler]]` run (a deleted title has no tags, so type/tag runs can't catch it).
- **Consecutive leading comments in a widget body stack as NESTED void widgets**: each `<!-- … -->` before the body's first widget parses as a `void` widget whose chain nests — N leading comments = +N widget-tree depth on EVERY surface rendering that body ($hgsd.list's three body-top comments are the `voidx3` in every measured bench path; a fourth comment ate exactly one level of the flattening win). A lone comment directly before a widget does not chain. When flattening a body for depth, fold commentary into existing comment nodes instead of adding new leading ones.
- **Below an inhibiting `$refresh` gate, cache on a state fingerprint — never on the passed change set**: a descendant widget's `refresh(changedTiddlers)` only ever sees changes the gates ABOVE it admitted. Row-fragment member edits never pass the engine's outer derivation gate (type-gate emits only for `$:/tags/hypergsd/Type`-tagged tags), so a per-row whitelist cache keyed on "did a member change in this pass" never invalidated — permanently stale (probe-proven). The sound key reads CURRENT wiki state per descent — refresh.js fingerprints the tag-index membership + members' change counts (`wiki.getChangeCount`, the engine's own `<<changecount>>` primitive — collision-proof where modified stamps are not; ~3.9 µs vs the 30.4 µs derivation it guards) — reproducing the shipped semantics (an upstream change lands on the next descending pass) at ~zero steady-state cost. Heavy dashboard item-edit refresh −11–17%.
- A bare single-bracket run around a hyphenated word (`[no-realm]`) does not parse; write `[[no-realm]]`.

## `action-listops` prefixes subfilters with `[all[]] `
Every `$subfilter` value is evaluated as `"[all[]] " + subfilter`, so its first run is never actually first. All the position rules above apply to every subfilter operand — prefer `[[literal]]` and `<variable>` forms.

## HTML element interiors parse inline — blank lines form no paragraphs
Inside a wikitext HTML element (`<label>`, `<span>`, `<div>`…), a blank line never starts a paragraph; it is inline whitespace, and `\whitespace trim` eats the run entirely (elements butt together). Spacing needs a literal `<br/>` (inside any reveal gate, so it cannot dangle when hidden) or a container rule. Paragraphs only form in block context — the plugin's own modal chassis hit this and ships a literal `<p>&nbsp;</p>` for the same reason.

## `<$view>`/`<$link>` without an explicit tiddler silently read currentTiddler
Parameterising a control's write target is only half the retarget: every implicit READ (`<$view field=…>`, `<$list>` over `[all[current]]`) still follows currentTiddler. Audit both directions when adding a target parameter — the harness catches it only if a case asserts the displayed value.

## `tm-navigate` must be dispatched on the navigator widget, not rootWidget
`$tw.rootWidget.dispatchEvent({type: "tm-navigate", navigateTo: t})` does nothing in a booted wiki: the handler lives on the NavigatorWidget, which services the event on its bubble-up path — a rootWidget dispatch never reaches it. In page context, walk the widget tree for the navigator and dispatch there (`$tw.story` does not exist in these wikis):

```js
let nav = null;
(function walk(w) {
  if (nav || !w) return;
  if (w.parseTreeNode && w.parseTreeNode.tag === "$navigator") { nav = w; return; }
  if (w.children) w.children.forEach(walk);
})($tw.rootWidget);
nav.dispatchEvent({type: "tm-navigate", navigateTo: t});
```

`tm-modal` is the opposite: it DOES work from rootWidget (`{type: "tm-modal", param: "$:/plugins/yan/hypergsd/ui/new-gsd-modal"}`) — the core handler for it sits at the root. Navigation-by-JS is for tests only; user-facing code navigates via widgets.

## Fakedom routes `style` into `_style`, not `attributes`
In the fake DOM, `setAttribute("style", …)` populates the element's style proxy (`el._style.display`); `attributes.style` stays undefined. Structural assertions must read `_style`/`el.style.display`. And a top-level wikitext HTML element gets wrapped in a `<p>` — probe `children[0].children[0]`, not `children[0]`.

## List-field appends dedupe by MOVING an existing entry to the end
`$action-listops` with `$subfilter` (and `tags` appends): re-adding a title already in the list field silently reorders it last instead of duplicating. Harness assertions on post-add list contents must expect the moved position.

## A procedure invoked in a filter-valued ATTRIBUTE half-parses and leaks source fragments
`list-filter=<<my-procedure>>` — the picker received pieces of the procedure's SOURCE as its option list (attribute-position macrocalls of procedures that render text via widgets are not a filter-string transport). Ship the literal filter string in the attribute; keep dynamic exclusion out or compute it where the attribute is consumed.

## Plain-text `<variable>` in a wikitext body parses as an HTML tag and vanishes
A procedure rendering filter **text** must wrap every piece in `<$text text="…"/>` (attribute values keep `<var>` literal and preserve inner spaces); adjacent text nodes also lose run separators to `\whitespace trim`, so leading spaces belong inside the text values.

## Subtractive `-[<var>]` runs resolve only through a rendered widget scope
A `{{{ … }}}` transclusion in scope excludes correctly, but `wiki.filterTiddlers(text, contextWidget)` leaves the target in — always evaluate picker filters the way the consuming widget does.

## Array field values serialise unbracketed
`addTiddler({f: ["Multi word"]})` stores `Multi word`, which titlelist parsing splits into two titles; multi-word list entries in fixtures need the `[[…]]` string form (production writes via `$action-listops` always bracket correctly).

## Space-separated filters inside `<%if%>` are alternatives (OR), not a chain
`<%if [is[current]tag[A]] [is[current]tag[B]] %>` fires for either — how `list-item/complete.tid` covers actions and projects. For AND, nest the ifs: a single two-filter gate once shipped a visible repeat box on undated tiddlers that the harness caught.

## `<%if%>` / `<%endif%>` must balance exactly
The conditional shortcut has no balance validation: an orphan or duplicated `<%endif%>` renders as literal text in the page. Check that `<%if` count equals `<%endif%>` count per file when editing conditional chains.

## An empty `<%if%>` branch transcludes the condition's output
The shortcut compiles to a `$list` over the condition's output; a branch whose body is empty or whitespace-only falls back to the list widget's default template and renders each output ITEM as a transclusion — an existing title renders its tiddler, a non-existent one a missing-link (live case: a warning gate leaked "no-realm" as a missing-link and the linked tiddler's own content inside "visible" branches). Every branch needs real content — a `<!-- comment -->` is enough. Space-separated expressions in the condition are OR'd; prefix runs (`:and`, `:filter`) chain AND onto their own expression only.

## Distinguishing "never created" from "exists but empty"
`has[field]` is false when the field is missing OR holds an empty value, so `!has[list]` cannot separate a pristine state tiddler from a deliberately emptied one. Use `!is[tiddler]` to select a state tiddler that does not exist at all; `is[tiddler]` matches any existing tiddler regardless of field values.

## `:filter` rebinding and membership

Inside a `:filter[...]` run, `currentTiddler` is rebound to each candidate being tested. A filter like `:filter[match<currentTiddler>]` matches every candidate against itself. Capture the outer title in a `$let` variable before the run. Similarly, `:filter[enlist<list>]` keeps every candidate (the parameter list is non-empty regardless); membership testing needs `:filter[enlist<list>match<currentTiddler>]`.

Position decides what sees the rebound item: variable RUNS rebind (`:map[<currentTiddler>]` emits the item), `all[current]` inside a `:map[subfilter<var>]` rebinds (the engine's group filters ride exactly this), but an OPERAND-position `<var>` inside the subfilter-evaluated string resolves against the AMBIENT scope — `gsd_contact<currentTiddler>` inside `:map[subfilter<per-contact-filter>]` read the page's currentTiddler and silently matched nothing. Per-item values must arrive as sources (`all[current]`, variable runs) or input-driven operators; widget-scope values reach operands only when bound in wikitext above the filter (dependants.tid's `match<viewing-title>` is load-bearing, not redundant).

## Variable-transported filter strings: run-bracket lead, attribute transport

A filter string arriving as a `subfilter<var>` operand must LEAD with a run bracket or a `:` prefix — a leading bare operator (`tag[x]y[z]`) reparses as "Filter error: Missing [" (with a spurious "deprecated regexp operand" warning when the text contains `$:/…` slugs), while the same text wrapped once (`[tag[x]y[z]]`) evaluates cleanly. Every engine-transported filter (the GroupBy members' `hgsd-group-filter`) leads with `[` for this reason. Conditional splicing of such strings: then/else operands cannot carry bracketed text at all, but a plain attribute CAN — `<$let gate-run=":filter[subfilter<gate-text>]"><$let gate-text="[all[current]get[field]…]">` round-trips brackets and `<var>` references verbatim (both stay unevaluated data), `then<gate-run>` transports the whole string wholesale, and the symbolic `<var>` references inside resolve only when the assembled filter is finally evaluated, against the binding `$let`'s scope.

## Titlelist-parsing operators: `enlist-input[]`, `listed[]` — and the back-reference membership gate

`enlist-input[]` parses each INPUT title as a titlelist: a bare single-title field value ("ZZ Alice") splits into the words ZZ and Alice. It belongs on genuine titlelist fields (`gsd_prerequisites`, `list`), never on plain text fields — there, plain `get[field]` emits the whole string for `match[]`/`compare[]`. Dually, `listed[field]` matches only titles the field's TITLELIST parse contains (findListingsOfTiddler → parseStringArray). Together these make a precise multi-value membership gate with no regex and no operand-set operator (there is NO `intersect` operator — only the `:intersection` run prefix; writing one yields filter errors): `[all[current]get[field]listed[list]match[<state-tiddler>]]` is non-empty exactly when the item's field value is an entry in the state tiddler's genuine titlelist `list` field — multi-word values survive because the selection side is a real titlelist.

## Action widgets fire only via action strings

Action widgets (`$action-setfield` etc.) are inert when rendered in a widget tree — they execute only when invoked through an action mechanism (button `actions`, checkbox `checkactions`, `invokeActionString`, eventcatcher handlers). Never build "reactive guards" expecting actions to run on re-render.

**Render-then-invoke trees see a PRE-action snapshot:** a trigger pattern of `tree.render(container)` followed by `tree.invokeActions(tree, event)` evaluates EVERY filter at render and fires every action afterwards — so all passes' `$list` membership is fixed against the state before any action ran, and earlier actions' writes are invisible to later filters (they still fire for render-time members). A raise and a date rollover in one run therefore see the same old stored date: one banner per occurrence by construction, not by ordering. Any multi-pass procedure run this way must be reasoned about as one atomic snapshot, never as sequential passes.

## `<$select>` takes only option/optgroup children

Nothing that renders a DOM element may sit between `<$select>` and its options — `<$reveal>` wraps its content in a `span`, and engines render only direct option/optgroup children, so span-wrapped options exist in the DOM but never display (leniency varies by OS select-widget backend, not engine version). For branch selection inside a select, use the `<%if%>` conditional shortcut (compiles to a `$list`, renders no element). Note that `HTMLSelectElement.options` collects DESCENDANT options on every engine, so DOM-count probes cannot detect this — assert no `:scope > span` instead.

## Action-mode checkboxes: `filter` attribute + buster for reactivity

A checkbox without `tiddler`/`field` runs in action mode: the `filter` attribute (evaluated with the widget as context) determines the checked state — non-empty output means checked — and `checkactions`/`uncheckactions` fire on click. `checked={{{…}}}` is inert. Action-mode checkboxes do NOT re-render when the tiddlers their filter reads change (their attributes never change, so a refresh descent ignores them). When such checkboxes must track state visually, wrap the region in a `<$refresh>` carrying a ''buster'' attribute (any non-`subfilter` attribute; a value change forces `refreshSelf`, recreating the children).

Three traps in this area, all hit in the Fragments settings work:

- **A `filter={{{ test }}}` attribute evaluates the TEST at render** — the checkbox then filters on the test's OUTPUT (usually empty: a permanently unchecked box). The filter attribute must be a LITERAL string; variables inside it resolve at filter-evaluation time, which is what you wanted.
- **Checkbox action strings do not resolve enclosing variables** — loop variables and `$set`/`$let` values referenced in `checkactions`/`uncheckactions` arrive as the LITERAL `<var>` text (an unknown variable in a filter run falls back to the literal title, which then gets written as text), while a select's `actions` string resolves its `$let` variables fine. When the checked state and the write both key on one tiddler, prefer a PLAIN field checkbox (`tiddler=`, `field=`, `checked=`/`unchecked=`/`default=`) — no actions, no transport, native refresh.
- **`<$checkbox>` with only `unchecked=` set renders CHECKED on an empty filter result** — the widget's list logic treats "neither value found, only unchecked specified" as absence-of-unchecked = true; the clean way to build ticked-unless-suppressed boxes.

## `qualify` is per-transclusion-chain, NOT per row

`<<qualify "$:/state/x">>` appends `-hashString(every transclusion variable in the parent chain)`. Inside a list, every row's fragment transclusion sets the same `transclusion` marker (the fragment title) — so all rows of a list hash identically and SHARE one qualified state. A per-row `<$button set=…>` then carries a render-time `setTo` computed against the shared value: once one row opens the reveal, every other row's click writes the same value onto an already-equal state — no change event, the button looks dead (the contextualise bug). Per-row state: build the title from the row item (`$:/state/x-<currentTiddler>` via filtered transclusion), never qualify. Corollary: a per-row state title keeps state shared when one item renders in two lists — usually the desired behaviour.

## A `\procedure` invoked in ATTRIBUTE position yields its body, not its output

`<$let x=<<myproc>>>` captures the procedure's DEFINITION text as x's value(a `$refresh` subfilter became the literal wikitext body). Text-position invocation (`<<myproc>>` as wikitext, or `<$transclude $variable=…>`) returns the rendered output. When a variable must default to a procedure's output, don't self-invoke in the attribute — either inline the derivation where it's consumed or duplicate the small composition as text.

## An undefined variable in a `$refresh subfilter` inhibits the row permanently

`<$refresh subfilter=<<undefined-var>> >` resolves to nothing usable and refresh.js never permits — the frozen subtree stops reacting to ALL changes while looking perfectly rendered(view-body-project's `hgsd-row` alias called the row composer outside the engine, where the per-list whitelist `$let` didn't exist; contextualise worked on dashboards but looked dead on project pages — the button still SET the state, which then surfaced as an already-open reveal when the same action rendered elsewhere). Fix pattern: ship a same-named `\procedure` default next to the composer so the gate resolves on every path; a `$let` of the same name shadows it per list.

## A failed server restart serves stale plugin files silently

`pkill -f "listen host"` matches nothing when the actual cmdline is `node …/tiddlywiki --listen` (host/port args absent or split), and zsh job-control PIDs printed after `(npm start &)` look like kill confirmations. A stale server happily serves pre-edit plugin bundles — probes pass against old code while the edit "does nothing". Always verify by port: `ss -tlnp | grep <port>` → kill the holding pid → start → confirm the served shadow contains the new marker text (`$tw.wiki.getTiddlerText(shadow)` in-page) before believing a live test.

## A modal opened outside the story navigator navigates to a tiddler named "undefined"

`modal.js` wraps the modal body in its own `$navigator` whose `story`/`history` attributes it captures from the DISPATCHING widget's scope (`getVariable("tv-story-list")`). Open a modal from outside the story river's navigator (keyboard shortcut, console `$tw.rootWidget.dispatchEvent`) and the capture is undefined → the modal's navigator writes navigations from inside the modal (created-tiddler opens, any `<$action-navigate>`) to a tiddler literally titled "undefined" — the story list never sees them. Fix: pass `tv-story-list`/`tv-history-list` in the `tm-modal` paramObject (it overrides the capture). Related modal facts: an edit-text's `focus="true"` never takes in modals (modal.js appends the wrapper AFTER rendering, so `focus()` lands on a detached node), and a bare `tm-focus-selector .gsd-new-modal` grabs the OLD modal's input because a replaced wrapper lingers ~400ms for the close animation — scope to `.tc-modal-wrapper:last-of-type …`.

## A triple-brace attribute holding a multi-item `:map` silently evaluates EMPTY

`<$let keys={{{ [enlist<titles>] :map[...] }}}>` yields "" whenever the mapped input has more than one title (single-item works, so hand probes look fine — this cost hours). The same trap bites other run prefixes and even plain operators: a `{{{ … :and[…] }}}` returned only the FIRST item, and `{{{ …tag[…] }}}` truncated likewise — triple-brace `$let` attributes are single-value territory; treat ANY multi-item filter output there as suspect and keep run-prefix expressions in `<$list filter="…">` attributes, which evaluate correctly. Also: `:and[enlist<var>…]` misfires even in `$list` attributes (returned non-empty for disjoint sets) — intersect via the proven `:filter[enlist<A>match<currentTiddler>limit[1]]` shape with `$list` as the conditional instead, and `<%if%>` conditions cannot carry run prefixes at all. `:map` defaults to FIRST-result-only — `:map:flat[...]` returns every result (needed for multi-key items like tags); dedupe+order in ONE merged run — `+[unique[]sort[title]!match[]]`, empty-string keys dropped. An earlier claim that a separate `+[unique[]]` append does not dedupe did not reproduce on 5.4.1 (the `+` prefix routes through and.js's clear-then-pushTop, so both forms dedupe identically — probed over a `:map:flat` output); the historical failure was most likely this triple-brace empty-evaluation itself.

## Applying a sort (or any transform) to a list: compose a STRING, never pipe through `subfilter`

The `subfilter` OPERATOR does not reorder its input: `[enlist<A C B>] subfilter<"+[sort[x]]">` returns A C B unchanged(it passes its input to filterTiddlers as `source`, but a leading `+` run does not sort the seeded input). And a macrocall INSIDE a quoted filter attribute stays literal: `filter="[enlist<x>] <<sort-expression>>"` treats `<<sort-expression>>` as a title. The working idiom for injecting data-held filter text (sort expressions, member filters): compose the whole loop filter as a string of VARIABLES and pass it whole — `<$let loop-base="[enlist<hgsd-titles>] :filter[…]" rows-filter={{{ [<loop-base>] [<sort-expression>] +[join[ ]] }}} >` then `<$list filter=<<rows-filter>>>`. Bracketed filter text is safe inside a quoted `$let` attribute (it is data there, never scanned); an EMPTY sort-expression joins to a no-op.

## A close-tag in the WRONG ORDER renders literally and mangles everything below it

`<$qualify>…<$let>…</$qualify></$let>` — TiddlyWiki's parser only closes the TOP of the open-tag stack; `</$qualify>` with the `$let` still open becomes literal TEXT in the output and the qualify never closes, silently restructuring the rest of the file (symptoms far away: filters evaluating empty, widgets after the leak misbehaving). Counts of open/close tags balance, so a count-based audit misses it — check ORDER, and always print the full rendered text once when a wikitext edit behaves inexplicably (a leaked `</$…>` in the dump names the spot). Also: a dropped brace in a `{{{ … }}}>` triple-brace attribute (two closing braces) produces no parse error — the attribute value silently becomes garbage; byte-compare against a working sibling line.

# Stylesheets

- **Transcluded images carry their own square sizing — a constraint to design around, not fight**: core image svgs render as inline `<svg>` elements stamped with the file's own `width`/`height` attributes (core ships 22pt square), and the glyph centres in that box (`preserveAspectRatio` default). CSS that clamps only `height: 1em` leaves the declared width standing — a 29px box under 14px-tall ink whose empty flanks reach invisibly under neighbours. Respect the square: scale BOTH dimensions together (the fold-chevron rule clamps width and height to 1em), or pass explicit `width`/`height` attributes to the `<$image>` widget; when spacing matters, measure the glyph's ink in a screenshot, not the svg box.

- **Stylesheet tiddlers render through wikitext**: the typography rule converts a literal `--` to an en-dash (U+2013), which silently invalidates CSS custom properties (`--x: v` arrives as `–x: v` and the declaration is dropped). Write the dashes as `&#45;&#45;` entities — entities decode after the typography pass.
- **Widgets do not parse inside quoted attribute values:** CSS like `option[value="<$text text=<<var>>/>"]` emits the widget source literally into the stylesheet. Emit dynamic text inside a quoted attribute with a filtered transclusion in text position — `option[value="{{{ [<var>] }}}"]` — and keep `<$text …/>` for block/text positions.
- **A stretch class means "fill the host row", and the host's width decides what that is:** `flex: 1 1 0` on a control resolves to its natural width while the host shrink-wraps (`width: fit-content` — the panel chassis `.hgsd-capture`), but grows the control to the row's edges inside a full-width host (a modal body). Copying a panel row's classes into a full-width surface silently turns the natural-width input into a full-width one — keep the flex+gap row pair, drop the sizer class. Worked example: new-gsd-modal's title row reuses the pick-row pair without `hgsd-sizer-select` for exactly this reason.

# Print layout

- **There is no print mode:** `tm-print` is just `window.print()` (core story.js) — paper is the current DOM minus what `@media print` rules hide. Vanilla's print rules strip chrome only (`.tc-sidebar-header`, `.tc-topbar`, `.tc-tiddler-controls`); core carries no content-conditional print logic and no beforeprint/afterprint handlers. Hiding plugin UI on paper means `@media print` display:none rules over hook classes.
- **`@media print` adds no specificity:** a `display: none` at (0,1,0) loses to a same-specificity display rule in any stylesheet tiddler sorting later in the `$:/tags/Stylesheet` tag list (default title order — `…/stylesheet` sorts after `…/print`). Worked failure: an add-row carrying `.hgsd-sizer-droplist` (display: flex from the base stylesheet) stayed visible on paper under `.hgsd-pick-append-row { display: none }`. Fix by structure, not specificity: hide a wrapper element that carries no display rule of its own — a compound selector or a list-after ordering pin only relocates the fragility.
- **Table cell alignment is a presentation attribute:** the table parser emits `align="center"`/`left`/`right` from the whitespace padding of a cell (`| A |` centres; core table.js), and presentation attributes sit at the BOTTOM of the cascade — any author rule beats them. Core ships `.tc-control-panel table > tbody > tr > td { text-align: start }`, so padded cells centre standalone in the story river but go start-aligned inside Settings tabs. Alignment that must survive context needs a class rule.
- **Print popups inherit plugin stylesheets:** `tm-open-window` renders `$:/core/ui/PageStylesheet` into the popup document (core windows.js), so one `@media print` rule set covers both the print-page button/Ctrl+P and TiddlyTools-style print windows.
- **Paper keeps two channels:** browsers drop background fills when printing (unless `print-color-adjust: exact`, which forces ink), so a selected state legible on paper must change its border and text colour (the status pills' shape). A fill plus white-ink-only selection prints white text on white paper — invisible. Related: `page.emulateMedia({media: "print"})` applies print media queries in the live viewport but still paints backgrounds — fill-dropping is a print-pipeline behaviour to reason, not screenshot.
# Browser probes and $:/StoryList safety

- **NEVER write, reset, "restore", or otherwise manage `$:/StoryList` — not during setup, not as cleanup.** The story list is the user's live list of OPEN tiddlers (their browsing session, shared across every browser window pointed at the wiki). "It looked empty when my session started" is NOT a baseline to restore to — the user's own browser may hold tiddlers open regardless of what the probe session sees. Don't close tiddlers, don't clear the list, don't "clean up" navigation you did. Test cleanup means exactly one thing: DELETE THE SCRATCH TIDDLERS YOU CREATED (distinctive ZZ-prefixed titles, plus any temp/state tiddlers your tests wrote) — nothing else. If a probe must open a tiddler, prefer navigation that appends naturally; the resulting open tiddlers are the user's to close, not yours. (Standing user instruction.)
- If story corruption ever DOES need manual repair: restoring **in-browser is not enough** — an open playwright page keeps autosaving its in-memory story back to the server, overwriting any disk-level repair and spawning `.sync-conflict-*` files. Correct sequence: close the playwright session → write the `tiddlers/$__StoryList.tid` file → restart the server (filesystem editions do NOT hot-reload disk edits) → verify with a fresh page.
- `localStorage.clear()` in a probe does not isolate state — the story lives in the wiki file server-side; a permalink (`#Title`) PREPENDS to the existing story rather than replacing it.
- A page's own output can be distinguished from story residue by the fact that residue always appears appended, once per previously-open tiddler (e.g. every open Project tiddler contributes its panel's list titles to `.gsd-list-title` scans).
- **Selection state differs per control in fakeDOM/probes:** radios mark selection via the label class `tc-radio-selected` — the input's `checked` ATTRIBUTE is never set — while checkboxes DO set the `checked` attribute. Collectors must branch on both signals (cost a false-failure debugging cycle).
- **`{!!field}` is wikitext TEXT substitution — literal inside filter expressions.** In a filter attribute it is not the current tiddler's field value but the literal string `{!!field}`(every sort option rendered empty because a lingo lookup queried a tiddler named `{!!sort-key}`). Use `[all[current]get[field]]`, or bind the value first and use `<var>` operands — and remember a `$list variable="x"` loop does NOT rebind currentTiddler, so `all[current]` is the page, not the item.
- **Wikitext character formatting renders as `<em>`/`<strong>`, not `<i>`/`<b>`**: `//text//` produces `<em>`, `''text''` produces `<strong>`(a browser check for the italicised "include ungrouped" label queried `querySelector("i")` and reported the working italics as missing). Probes and assertions must query `em`/`strong`. `//…//` around a transclusion (`//{{…}}//`) parses fine — the transclusion is ordinary inline content.
- fakeDOM stray-text guards must branch on the negative: text nodes are NOT fakeDom elements tagged `#text`, so `n.tag === "#text"` guards NEVER fire (they pass vacuously — a genuine stray-`>` regression once stayed masked this way for a day). Correct shape: `if (n.isTiddlyWikiFakeDom) {recurse children} else if ((n.textContent||"").trim() === ">") stray++;`. Every render harness should carry such a guard; count strays across ALL renders, not just assertions' targets.

- **A fakeDOM member render that comes back EMPTY after a sequence of earlier renders, while the same shape renders fine in a fresh boot and a real browser, is a harness artifact** — verify in the browser before chasing it in the harness (a contact-section render went blank mid-test while the browser rendered it perfectly; the forensics found nothing in the plugin).
- **`$tw.wiki.addToStory([...])` called from a playwright `page.evaluate` crashed the page** ("Linked List only accepts string values") — set the story via `addTiddler({title: "$:/StoryList", list: [...]})` instead.
- **Browser-side `addTiddler` against a served wiki folder autosaves real `.tid` files** into `tiddlers/` (the filesystem + tiddlyweb plugins): fixture tiddlers from a visual probe must be deleted from DISK afterwards, not just from the browser session.

# Refresh and focus

- A `$let` whose value derives from a tiddler the user is typing into will `refreshSelf` on every keystroke and recreate its whole subtree — if an `edit-text` input sits inside, focus is lost per character. Keep such lets narrow (wrap only the dependent widget) or avoid the let: read the temp inline in the gate (`[<temp>get[field]!match[]] :and[…]`) and pass the value as an inline `{{{ … }}}` attribute on the consuming widget — then only that widget's subtree rebuilds.

# Tiddler namespaces and persistence

- `$:/state/*` and `$:/temp/*` tiddlers are excluded from saving — they vanish on every reload. Anything a user sets that should survive sessions (selections, preferences) belongs under `$:/config/*`. Symptom of getting it wrong: UI shows the pristine/all-defaults view with unticked controls after each reload while the underlying feature silently resets.

# Sub-plugins and plugin fields

- The sub-plugin mechanism lives in the `parent-plugin` field (nest under a parent in the control panel chooser; sub-plugins cannot nest further) and `dependents` (plugins installed alongside this one; non-recursive). `name` is the display title. These are documented under PluginMechanism — never claim a mechanism is absent from one misremembered field name (`plugin-prereqs` does not exist; the real fields do).
- Plugin folders under `plugins/` auto-load (PluginFolders): at startup boot.js scans the wiki's own `plugins/` directory ONE level deep and loads every plugin folder it finds, unconditionally — the `plugins` array in tiddlywiki.info plays no part (it resolves library plugins from the installed package's plugins dir / `TIDDLYWIKI_PLUGIN_PATH` via `findLibraryItem` only). So a new local plugin folder goes live by restart alone, no config edit. Two consequences: (a) a wiki cannot EXCLUDE a plugin that sits in its plugins/ folder — deleting/moving the folder (or, in a test fixture, removing the symlink) is the only off switch, which is exactly how the degradation fixture simulates sub-plugin absence; (b) a fixture wiki loads plugins from ITS OWN plugins/ folder — a freshly created sub-plugin needs a symlink added there or it silently never loads (symptom set: tag list enumerations miss the type, lingo family counts come up short by exactly the plugin's keys). Folder name and shadow-title prefixes may differ from the plugin title.
- Gate core UI on an optional plugin's presence with `[[<tag-list-member>]get[title]]` — the `title[X]` operator emits unconditionally (existence-blind, like any literal run), so `[all[shadows+tiddlers]title[X]]` is always truthy.
- A `:filter[]`/`:map[]` operand is a SINGLE filter run — multi-run expressions fail with "Missing [". Constructor runs REPLACE the accumulated output (no union); append parts with `+`-prefixed runs over the accumulator (`+[addsuffix<var>]`).
- Moving a list tiddler between plugins changes its title — every visibility seed (`$:/config/…/visibility/<full-title>`), tag pin, and cross-plugin transclusion must be re-pointed, or the list silently loses its defaults and ordering.
- Building a newline in filter context: entities (`&#10;`) do NOT decode inside `{{{ }}}` attributes, and a filter ending in an empty operand (`op[]]`) breaks the attribute scanner. Working recipe: `<$let encoded-newline={{{ [[%0A]] }}}>>` then `<$let newline={{{ [<encoded-newline>decodeuricomponent[]else[newline]] }}}>>` — and use it as a runtime operand (`join<newline>`, `addprefix<newline>`). When fixing the stray-`>` brace bug, the malformed bytes are three braces + two angles: a four-brace search/replace literal silently matches nothing.
- Plugin translations are blocked until bundled sub-plugins land (TiddlyWiki5 PR #8957): the core language switcher activates only the selected language plugin plus its `dependents` chain, and `plugin-priority` (ascending, later wins) governs shadow conflicts at unpack. Harness renders that use `<<lingo>>` must import `$:/core/ui/PageMacros` + `tag[$:/tags/Macro]` (not just `$:/tags/Global`).
- Python f-strings collapse `{{`/`}}` to single braces — a `f"...Caption}}"` writes a one-brace transclusion into the file. When generating wikitext containing `{{...}}` via f-strings, double them (`{{{{`/`}}}}`) or use plain string concatenation.
- `<<lingo Key>>` works in BODY position (macro bodies are wikified) but in ATTRIBUTE position it yields the raw `{{...}}` text — attributes must use direct transclusion: `tooltip={{$:/language/...}}` (core's own pattern). Also true for any macro whose body contains transclusions.
- `importvariables` flattens all definitions from Global-tagged tiddlers into one scope: a file-level `lingo-base` in an imported widget leaks and gets shadowed by whichever imports last. lingo-base + `<<lingo>>` only in TRANSCLUDED tiddlers; Global-tagged files and attribute positions use full-path `{{$:/language/...}}` transclusions. `\whitespace trim` drops separator whitespace between inline nodes — compose multi-part labels as one filter string.
- Renaming a plugin prefix: visibility-seed `.multids` files compose titles from a `title:` base ending in `$:/` plus bare `plugins/<name>/...` KEYS — those keys are path-as-title and must carry the TITLE path (`plugins/yan/hypergsd/`), never the disk folder path (`plugins/hypergsd/`, no author segment). A mismatched seed dies silently: every gate falls back to `show`.

# Newer TiddlyWiki features (5.2 → 5.4.1; release notes in the TiddlyWiki5 repository at https://github.com/TiddlyWiki/TiddlyWiki5)

- **No batch-write API:** `wiki-bulkops.js` exports only `renameTiddler`/`relinkTiddler`. `$tw.wiki.addTiddlers(array)` is the batch idiom (one refresh cycle for N writes; internal-stable, used by core's parser and testcase widget).
- **`$tw.utils` deprecations (5.4.0):** `startsWith`/`endsWith`/`trim`/`repeat`/`sign`/`stringifyNumber`/`addClass`/`removeClass`/`toggleClass`/`hasClass`/`tagToCssSelector` and friends moved to `utils/deprecated.js`. `parseDate`/`stringifyDate` are NOT deprecated (still in `boot/boot.js`, used across core) — safe to build on.
- **Widget lifecycle:** `destroy()` override is supported (added 5.3.0, reverted 5.3.1, final in 5.4.0) — override it to release DOM listeners. `Widget.prototype.addEventListener` no longer overwrites old listeners (5.3.7).
- **Startup modules:** may return promises (5.4.0); `exports.platforms = ["browser"]` keeps browser-only work out of node-server processes; JS edited inside a DRAFT tiddler does not execute (5.4.0) — restart or save before testing module changes.
- **No date arithmetic in filters:** core 5.4.1 has no `addticks`/date-math operator. Date maths needs a `module-type: filteroperator` JS module (operator: date string in → date string out). `format` operator converts Unix timestamps to TW date strings (5.3.0); epoch/weekday/day-of-year tokens exist in DateFormat (5.2.0/5.2.4).
- **`<now>` in filter position is NOT a raw date string:** the `now` macro resolves to its human-formatted output ("00:02, 31st August 2026") — feeding it to date parsing yields 1900-defaulted garbage that can still LOOK valid. Bind the raw format with the `[UTC]` qualifier (the bare format renders LOCAL time) and use the variable: `<$let now-raw=<<now "[UTC]YYYY0MM0DD0hh0mm0ss0XXX" >> >` then `[<now-raw>…]` (core's own `format:timestamp[]` default) (the macrocall closer needs the space-before-`>>` guard).
- **`$tw.utils.parseDate` never throws but can 1900-default:** outright garbage returns `null`, but partially-numeric strings ("00:02, …") parse positionally into 1900-based dates — guard with `isNaN(date.getTime())` AND treat null, and prefer normalising every written date to midnight UTC so rollover maths stays deterministic.
- **The `compare` operator: suffix order is `type:mode`** (`compare:integer:gt[…]]`, not `compare:gt:integer`) — and an unknown mode SILENTLY falls back to equality (a `lte` operand matches only exact equals, selecting nothing). Unparseable input scores 0, so it passes `lteq` against any positive operand — gate garbage out before comparing. String type orders fixed-width date strings correctly; "N…" sorts after every date.
- **Filter operator names are load-bearing and unknown ones fail silently (empty output):** the regex operator is `regexp` (NOT `regex`), `minlength` exists but `maxlength` does NOT (negate minlength instead), and `length` is a TRANSFORM (outputs title lengths), not a membership filter.
- **Attribute-layer filter escaping:** inside quoted attribute values a `\d`-style backslash is eaten (`regexp[^\d{17}$]` arrives as `^d{17}$` and matches nothing) and a `]` inside an operand breaks the attribute scanner (`regexp[[0-9]{17}]` swallows the rest of the tag). Prefer bracket-free forms (`minlength`).
- **`search-replace:g[-],[]]` must end its run:** operators appended after the `],[` operand chain get swallowed by its operand parsing — split into separate runs or use `split[-]join[]` instead.
- **`$action-createtiddler` ignores `$title`:** without `$basetitle` it calls `generateNewTitle` on the default "New Tiddler" (creating "New Tiddler 1, 2, …" and ignoring your intended title). Use `$basetitle=…` + `$overwrite="yes"` for a fixed title. Widget-bearing field values (e.g. a text field containing `<$transclude/>`) need triple-quoted attributes — single quotes break the parse.
- **`invokeActionString` parses in the CALLER's scope** — invoking from an outer widget leaves inner-scope variables (`<<target>>` procedure params) empty. Call it on the widget whose scope has the variables. And trees it BUILDS do not execute actions nested inside a `$variable` transclude — to run a procedure's actions programmatically, render a real tree carrying the transclude and call `tree.invokeActions(tree, event)` (or make the transclude a CHILD of a `$button`).
- **`inputActions`/`actions` attributes execute bare action widgets only:** `<%if%>` and `<$list>` are silently ignored there (same class as `$select` actions). Move guards into the VALUE filter — the else-subfilter form rebuilds empty pipelines with a bare variable: `[<pick>split[-]join[]addsuffix[000000000]minlength[17]else<current-value>minlength[17]]` canonicalises a pick and no-ops an empty one (writing the current value back).
- **Native date inputs fire `change` on SEGMENT completion** (month/day/year), not only on full commit — a `change`-driven save/rebuild handler therefore interrupts typing mid-entry. `inputActions` fires per `input` event regardless. Test focus behaviour with node-identity probes: mark the input (`data-probe`), dispatch the event, assert the marked node is still connected and focused — plus a write spy on `wiki.addTiddler` to see which tiddlers each event touches.
- **A widget/template whose change handler writes state that its own seeding scope reads rebuilds its subtree on every change** (the TiddlyTools EditDate template's `save`+pop-deletion is the worked example): the fix is to route commits through `inputActions` (which writes the real target directly) and suppress the internal save — e.g. the template's `confirm` flag when it gates the change handler.
- **Wikitext power:** `:let` run prefix assigns filter results to variables usable as operator parameters (5.4.0); `<$list-template>`/`<$list-empty>` and the `join` attribute on ListWidget (5.3.2); LetWidget (5.2.1); `:cascade` prefix (5.2.1); `substitute` operator (5.3.0).
- **Popups:** RevealWidget `clamp` attribute (`right`/`bottom`/`both`, 5.4.0) keeps popups inside their container — use for in-row pickers.
- **Modals:** `mask-closable` defaults to yes on 5.4.x (dismiss by background click) — set `mask-closable="no"` where the old behaviour matters.
- **edit-text:** `tag="input" type="date"` renders a native date input but stores the raw attribute value (yyyy-mm-dd) with no TW-date conversion; the `actionValue` variable carries the input's value to actions (5.2.1).
- **Field Editor Cascade (5.2.3):** register a custom editor template per field name so the standard EditTemplate renders e.g. a picker instead of a raw text row.
- **Alerts:** mechanism unchanged since 5.2 (`$:/tags/Alert` + `$:/temp/...`, ARIA polish in 5.4.0) — `$tw.logger.alert()` or hand-built alert tiddlers both current.
- **Cache discipline (5.4.0):** functions returning cached tiddler lists now return shallow copies — still never sort/mutate them in place.
- **Server split (5.4.0):** server-side core moved into `$:/core-server`; browser-only plugin code should not reach for server modules.
- **Keyboard shortcut config text is parsed verbatim:** `parseKeyDescriptor` splits on `+`/`-` and looks each token up in the named-keys table without trimming, so a trailing newline in a `$:/config/shortcuts/<name>` tiddler's text (the natural state of a `.tid` file, whose body always carries one) yields `parseKeyDescriptor` → null and silently kills the shortcut — `((name))` is resolved through that parse, so the trigger registers but never fires. Keep the config text ending exactly at the key descriptor; test with `parseKeyDescriptors("((name))")` returning a real keyCode, and remember dynamic rebuilds happen only when the trigger or config tiddlers change.
- **Core modals have no Escape handler:** `tm-modal` dialogues close only via the footer button, a `mask-closable` backdrop click, or `tm-close-tiddler` — pressing Escape leaves the modal open, which in Playwright sessions silently stacks a second modal over the first (locators then resolve against the bottom one). Also, a modal opened from a keyboard shortcut inherits `tv-story-list`/`tv-history-list` from the root widget, where they are empty — in-modal navigations then write to a bogus story unless the trigger passes `tv-story-list="$:/StoryList" tv-history-list="$:/HistoryList"` explicitly (the same trap the HyperGSD shortcut triggers document).
